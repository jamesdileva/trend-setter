# Sprint 02 — Database foundation, migrations, and durable events

- **Roadmap sprint:** Sprint 2 in [`../../sprint-roadmap.md`](../../sprint-roadmap.md)
- **Status:** In progress
- **Date:** 2026-11-11

## Goal

Create the local data layer before market or trading behavior depends on it: all core tables, Alembic migrations, repositories with centralized write ownership, and backup/restore tooling.

## Scope

Engine (`engine/`), per architecture.md §14 and implementation.md §2 (`database/` owns models, migrations, repositories, transaction helpers):

- `src/trendbot/database/models.py` — all core tables from architecture.md §14: `app_settings`, `credential_metadata` (reference only — never key material), `products`, `candles`, `strategy_configs`, `signals`, `order_intents`, `exchange_orders`, `fills`, `positions`, `balance_snapshots`, `risk_events`, `engine_events`, `backtest_runs`, `backtest_trades`, `daily_accounting`
- `src/trendbot/database/session.py` — `Database`: per-connection PRAGMAs (foreign keys ON, WAL, busy timeout), transactional session context manager, typed `DatabaseWriteError`, best-effort `write_failure()` health event
- `src/trendbot/database/types.py` — `DecimalString` (exact decimal strings; floats rejected) and `UtcDateTime` (timezone-aware UTC enforced, stored as naive UTC) column types
- `src/trendbot/database/repositories.py` — `CandleRepository` (deduplicated upserts, range reads to domain `Candle`), `FillRepository` (idempotent by exchange `entry_id`), `EngineEventRepository` (optional `dedupe_key` identity), `SettingsRepository` (upsert)
- `src/trendbot/database/backup.py` — consistent online backup (SQLite backup API), integrity check, restore into a clean database (refuses to overwrite)
- `src/trendbot/database/migrations.py` — `upgrade_to_head()`: backs up an existing non-empty database before migrating, runs Alembic, wraps failures in plain-language `MigrationError` with the backup path
- `alembic.ini` + `migrations/` (env.py, script template, initial revision autogenerated from the models; version table named `schema_migrations` per architecture.md §14)
- `pyproject.toml` — runtime deps: sqlalchemy, alembic

Unique constraints: candles on `(product_id, granularity, start_time)`, fills on `entry_id`, `client_order_id`, exchange order ids, event `dedupe_key`, `(name, config_hash)`, daily accounting `day`, positions `product_id`.

Out of scope: business logic writing to these tables (Sprint 4+ market data, Sprint 6 signals, Sprint 8 order pipeline), Alembic autogenerate tooling in CI, PostgreSQL (VPS addendum defers that decision).

## Acceptance criteria (roadmap Sprint 2 verification)

- [x] Fresh database initializes
- [x] Migrations upgrade from empty database (version-tracked in `schema_migrations`)
- [x] Duplicate candle/fill insert is safely deduplicated (unique constraints + `ON CONFLICT DO NOTHING`)
- [x] Financial values round-trip without binary-float corruption (decimal-string storage; floats rejected at the boundary)
- [x] Backup restores into a clean database (SQLite backup API + integrity-verified restore)
- [x] A failed write produces a visible health/error state (transaction rollback + `database_write_failed` engine event)

## Deviations & follow-ups

- The Alembic history table is named `schema_migrations` (configured in `migrations/env.py`) to match architecture.md §14's naming.
- Fill storage identity is currently `exchange_order_id:trade_id` (composite, documented in `fill_entry_key`): the typed `Fill` does not yet carry Coinbase's `entry_id` from the verified fills schema — that mapping lands with the reconciliation sprint and must switch the key to `entry_id`.
- `Database` is file-backed only; the in-memory special case was deliberately removed so durable state always lands on persistent storage (vps-deployment.md §9).
- Downgrade operations are autogenerated but unexercised — the documented recovery path for a bad migration is restore-from-pre-migration-backup (tested). Exercising `downgrade()` can be a later hardening item.
- Autogenerated migration files get relaxed lint (`E501`, `W291` via `per-file-ignores`); all other repo code stays at full strictness.
- Follow-up for later sprints: repositories for the remaining aggregates (orders, positions, daily accounting) arrive with their features (Sprint 6/8/9); this sprint shipped the four the roadmap's verification needs.
